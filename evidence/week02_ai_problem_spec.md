## 1. Business / System Problem
在無人機高空搜救與邊界巡檢任務中，紅外線熱成像受限於飛行高度（50–120 公尺）與俯視視角，地面目標（如受困人員、車輛）在畫面上成像微小（常小於 16×16 像素）且對比度低；長時間依賴搜救人員肉眼監看螢幕極易產生視覺疲勞，導致微小熱源漏檢，且高空影像傳輸頻寬受限，極需邊緣端即時智慧輔助。

## 2. Decision Point
在無人機邊緣運算晶片收到即時紅外線影格當下，即時判定該影格中「是否存在特定微小目標，以及目標在畫面中的精確邊界框（Bounding Box）」，以決定是否在地面站螢幕觸發聲光警報並自動框選追蹤。

## 3. Unit of Analysis
- **層級**：影格層（Frame Level）
- **Unit**：單張高空紅外線熱成像影格（Single IR Frame）
- **Input**：即時單通道紅外線熱影像矩陣
- **Target**：影像中目標之邊界框座標與類別 (x, y, w, h, class)
- **任務類型**：微小物件偵測（Small Object Detection）

## 4. Input
無人機紅外線相機即時擷取之單張灰階熱成像影格（如 640×512 解析度），以及當前飛行高度與焦距中繼資料（中繼資料僅作為推論後處理之實體尺寸過濾與換算使用，不輸入神經網路骨幹）。
*（嚴禁包含地面事後搜救回報之 GPS 軌跡或結案確認標籤，杜絕 Data Leakage）*

## 5. Target
影格中所有目標之真值邊界框與類別（Ground Truth Bounding Box & Class，如 `person`、`vehicle`）。針對長波紅外線微小目標之熱暈散效應，以熱源輪廓向外擴展 2 像素作為標註邊界之統一客觀準則。

## 6. Output
JSON 格式物件：
```json
{
  "frame_id": "frame_1042",
  "detections": [
    {
      "class": "person",
      "bbox": [320, 240, 28, 54],
      "confidence": 0.88
    }
  ],
  "alert_triggered": true
}
```
- **detections**: 偵測目標清單（含類別、座標陣列 $[x, y, w, h]$、信心度分數 0.00–1.00）
- **alert_triggered**: 是否觸發搜救警報（Boolean）

## 7. Baseline
- **現況（No-AI）**：人工全程肉眼盯視地面站螢幕手動搜尋熱點，單張評讀時間長，微小目標漏檢率高達 40% 以上。

- **簡單方法（Baseline）**：傳統數位影像處理之「熱訊號雙峰閥值分割法（Otsu Thresholding + 連通元件分析）」。運算耗時極短且不需訓練，但在地表日照強烈或環境雜波時誤報率極高。

- **複雜方法（AI）**：輕量化微小物件偵測模型（如 YOLOv11/YOLOv12 nano/small 經高空熱成像微調），必須證明在保持即時性的前提下，微小目標檢測率與抗雜波能力實質優於傳統閥值法。

## 8. Success Criteria
- **Technical**: 針對微小目標（像素面積 < 32×32）之 mAP@0.5 ≥ 0.75；對極小目標（< 16×16 像素）採納中心點常態化距離門檻與 IoU ≥ 0.3 作為輔助驗收指標，且核心類別（person）之 Recall ≥ 0.85。

- **System**: 無人機邊緣運算端（如 Jetson 平台）推論幀率 ≥ 30 FPS（單張延遲 ≤ 33ms），顯存佔用 ≤ 2GB，且峰值功耗不得引起系統過熱降頻。

- **Decision / Value**: 離線測試序列中每百影格之平均虛警次數降低 70%，且微小熱源漏檢率由人工基準的 45% 降低至 15% 以下。

## 9. Failure Criteria
- **模型層**: 人體目標在連續 5 個影格以上漏檢；對地表日照反光熱雜訊產生連續虛警（False Positive 頻率 > 每分鐘 3 次）；高信心度（> 0.90）卻嚴重框錯位置。

- **系統層**: 邊緣晶片過熱降頻導致推論幀率 < 15 FPS（畫面卡頓脫靶）；感測器進行非均勻校正（NUC 打快門約 0.5 秒）時產生畫面凍結殘影，系統未維持前一狀態而將殘影誤判為警報目標。

- **業務層**: 虛警頻率過高迫使搜救隊員關閉輔助系統；嚴重漏檢導致錯失黃金搜救時間。

## 10. HITL / Fallback
-**轉人工條件**: 當目標偵測信心度介於 0.40 至 0.65 之間（疑似微弱熱源），或自然界出現「熱交叉現象（溫差趨近 0°C）」導致畫面反差過低時，系統高亮黃框提示地面站飛手進行光學變焦二次人工確認。

-**最後決策者**: 搜救指揮官與無人機飛手保留最終確認權，系統僅作告警提示，不具備自主處置權力。

-**失敗接住機制**: 若邊緣運算模組異常或掉幀，系統自動降級為無運算之「純影像直傳串流」，並啟用基於 Otsu 的超溫警報備援機制，確保基本影像傳輸不中斷。

## 11. 最大 Assumption
假設在實際搜救高度（50–120 公尺）下，人體熱源與周遭環境在長波紅外線（8–14 μm）頻段具備至少 2°C 以上之可分辨溫差，且目標在影格中佔據面積至少達 8×8 像素。

# AI Review Record

## Finding 1 (目標太小、邊界太糊怎麼算)
- **AI Reviewer**: 人在畫面上常常不到 16×16 像素，而且熱源邊緣糊糊的，硬規定 IoU 0.5 才能框中太嚴格了，稍微歪個 2 像素就算答錯，根本測不出模型實力。
- **Decision**: Accept
- **Reason**: 說得沒錯，微小物件算 IoU 本來就很吃虧，不能死守標準規格，不然抓到人都會被誤判成抓錯。
- **Change**: 標註時統一往外抓多 2 像素當緩衝；驗收時針對 16 像素以下的小目標，改看中心點有沒有對準，IoU 放寬到 0.3 就算通過。

## Finding 2 (無人機高度跟焦距塞在哪)
- **AI Reviewer**: Input 寫了無人機高度跟鏡頭焦距，但 YOLO 神經網路只吃圖片矩陣，根本吃不下這兩個數字，寫進去反而讓介面定義很奇怪。
- **Decision**: Modify
- **Reason**: 神經網路雖然不吃，但這兩個數字在後台過濾超好用（能直接算出地面目標的真實長寬，把太大或太小的雜訊砍掉），不能全丟。
- **Change**: 不塞給神經網路硬吃，在規格中註明這兩項「只給推論後的程式算物理尺寸與過濾用」。

## Finding 3 (減輕 70% 負擔在離線根本沒法測)
- **AI Reviewer**: Success 寫「減輕搜救人員 70% 肉眼負擔」，但目前只有離線影片和照片，沒人真正飛上去測，這條要怎麼驗收？
- **Decision**: Accept
- **Reason**: 確實，離線測試沒辦法找搜救隊來打分數，必須換成電腦跑得出來的具體數字。
- **Change**: 換成離線量化指標：測試序列中「每 100 張影格的假警報次數降低 70%」，而且小目標漏抓率必須從人工的 45% 壓到 15% 以下。

## Finding 4 (要不要把 Baseline 換成超強 Transformer)
- **AI Reviewer**: Otsu 雙峰切門檻遇到大太陽地表整片發熱就爆掉了，要不要乾脆把比較基準換成最新的 RT-DETR 大型架構？
- **Decision**: Reject
- **Reason**: Baseline 的目的本來就是要找「最簡單的非 AI 方法」來對照，證明 YOLO 真的有增量價值；而且無人機上的小晶片根本跑不動大模型。
- **Change**: 堅持維持傳統影像處理的 Otsu 門檻法當對照組，只要證明 YOLO 在雜訊多的地形誤報率明顯更低就算達標。

## Finding 5 (熱交叉人體隱形與鏡頭打快門校準)
- **AI Reviewer**: 紅外線鏡頭每隔一陣子就會「打快門校準（NUC）」畫面會停住半秒，而且早晚地溫跟體溫一樣時人會直接隱形，這些物理限制你的 Failure 怎麼完全沒提？
- **Decision**: Accept
- **Reason**: 這兩個都是紅外線鏡頭常碰到的物理狀況，沒寫進去的話，系統在校準殘影時亂叫、或是遇到熱交叉整組漏看就算系統重大缺陷。
- **Change**: Failure 加入「打快門校準那半秒如果亂叫警報就算失敗」；HITL 增加「遇到熱交叉反差過低時，系統主動切換提示並讓飛手切可見光鏡頭手動確認」。

# Mini Defense 準備紀錄

- **Q1: 你真正要預測/檢索的是什麼？**
  -  在單張高空紅外線影格（Unit）上，以即時熱成像像素為 Input，偵測出微小人體或車輛之真值邊界框與類別（Target），並輸出包含目標座標、信心度與警報旗標的 JSON（Output）。
- **Q2: 不用你的 AI，Baseline 是什麼？**
  -  採用傳統影像處理的「Otsu 雙峰閥值分割法」。因為它不需模型訓練、能在微控制器上即時運算，是檢驗 YOLO 能否在複雜背景雜波中有效降低虛警並提升召回率的合理基準線。
- **Q3: 哪種情況下即使模型分數很高，你仍判定系統失敗？**
  - 若整體 mAP 達到 0.85，但錯誤集中在關鍵的人體目標（發生致命漏檢），或者推論延遲超過 66ms（FPS < 15）造成搜救畫面卡頓脫靶、虛警頻率過高迫使飛手手動關閉警報，在系統工程實務上即判定為失敗。
