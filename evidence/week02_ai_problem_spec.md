## 1. Business / System Problem
電商平台客服中心每日進線訊息量龐大，現行依賴第一線客服人員逐則閱讀並手動分流工單，單則平均需耗費 30 至 40 秒判讀。在尖峰時段易造成工單積壓與回覆延誤；且對於語意模糊的複合語句（例如同時出現「退貨」與「包裹送達」），不同客服人員的分類標準不一，導致轉單與二次處理成本增加。

## 2. Decision Point
在系統收到使用者發送的單則進線訊息當下，即時判定所屬意圖類別（`order_delivery`、`refund_return`、`account`、`product`），決定自動路由分派至對應的專業客服組別，或判定為低信心度轉交人工審核。

## 3. Unit of Analysis

- **層級**：訊息層
- **Unit**：一則獨立的客服進線訊息（Single Customer Message）
- **Input**：一則進線原始文字
- **Target**：intent class（意圖類別，如 refund_return、order_delivery 等）
- **任務類型**：分類／路由

## 4. Input
使用者發送之原始文字（如「我想退貨但包裹已送達還能辦嗎」）與進線時間戳記。（不包含事後結案碼或客服備註，杜絕 Data Leakage）
## 5. Target
該則訊息真實所屬的意圖類別標籤（Ground Truth Intent Class）：
- `order_delivery`（訂單／配送）
- `refund_return`（退款／退貨）
- `account`（帳號／登入）
- `product`（商品資訊）

## 6. Output
JSON 檔
```json
{
  "predicted_intent": "refund_return",
  "confidence": 0.92,
  "needs_human_review": false
}
```

- **predicted_intent** : 預測意圖類別（String）

- **confidence** : 信心度分數（Float）

- **needs_human_review** : 是否需轉人工覆核（Boolean）

## 7. Baseline

- **現在（人工）**：由客服人員逐則閱讀訊息並手動分流工單，平單則耗時 30–40 秒且規則不一。
- **簡單**：Week 1 的 src/rule_baseline.py 關鍵字比對（Accuracy = 0.950）。
- **複雜**：機器學習／深度學習分類模型，需證明能解決複合語意衝突並提供高於 0.950 的增量價值。
## 8. Success Criteria
- **Technical: Accuracy ≥ 0.970、Macro-F1 ≥ 0.960、**refund_return Recall8 ≥ 0.960。
- **System**: 單筆訊息推論 P95 Latency <= 150ms，系統可用性（Uptime）>= 99.9%。
- **Decision / Value**: 80% 以上進線訊息完成全自動路由，工單平均分派等待時間由 35 秒降至 2 秒內，跨組轉單率降低 40%。

## 9. Failure Criteria
- **模型層**: 包含複合關鍵字的句子持續被優先誤判為物流；高信心度（Confidence > 0.90）卻分類錯誤；涉及退款爭議的 `refund_return` 類別 Recall < 0.90。
- **系統層**: 單次推論耗時超過 500ms 造成對話卡頓；模型輸出非定義的 4 類標籤或回傳 Null。
- **使用/責任層**: 客服人員因分流錯誤率高而全面改回手動檢查，造成作業時間不減反增；高爭議客訴被誤派至一般諮詢組導致延遲超過 SLA。

## 10. HITL / Fallback
- **轉人工條件**: 當最高預測信心度 `confidence < 0.75`，或前兩名機率差距 < 0.15 時，自動標記 `needs_human_review = true` 並轉交人工初篩隊列。
- **最後決策者**: 第一線客服專員保有最終修正權，其修正紀錄自動回流資料庫以供後續模型迭代。
- **失敗接住機制**: 若分類服務逾時或中斷，平順降級回退（Fallback）至 Week 1 的 `src/rule_baseline.py` 規則；若規則未命中則派入通用人工接待池。

## 11. 最大 Assumption
假設當前展示資料集（`data/customer_intent_demo.csv`）中的 4 類意圖分佈與長度能代表線上真實對話，且大部分使用者會在進線第一句話中表達其核心訴求。

# AI Review Record

## ① Target 是否可驗證？
- **複合意圖與邊界界定**：目前 Target 定義為互斥的 4 選 1 類別（Single-label Multi-class）。但真實客訴常見「我想退貨，另外我昨天改密碼收不到驗證碼」這類跨領域語句，目前的標註資料與評估邏輯中，是否具備明確的「主意圖判定準則」以產出唯一的 Ground Truth？

-   **追問**：若兩位標註人員對同一筆模糊語句有不同分類見解，你的驗證集是用什麼客觀規則（如多數決、特定類別優先級）定出最終 Target？ 

## ②Input 是否可能包含未來資訊或不應取得的欄位？
- **特徵有效性與進線切分**：已明確排除事後結案碼，方向正確。但將「時間戳記」列入 Input，若後續模型為單純文字分類器，該欄位如何參與推論？若無具體特徵工程規劃，列入 Input 會造成接口定義冗餘。

- **追問**：真實對話中使用者常將一句話拆成多則短訊發送（如先打「你好」，兩秒後再打「我要退貨」），系統的 Input 究竟是指「單一網路封包文字」還是「對話連線後 N 秒內的合併訊息」？若只抓單則文字，遇到無實質內容的招呼語該如何處理？
## ③ Success / Failure 是否可驗收？
ㄦ- **指標落地性不足**：Decision/Value 指標列出「跨組轉單率降低 40%」與「分派時間降至 2 秒」，但在目前的開發階段（僅有 100 筆靜態展示資料集 customer_intent_demo.csv），缺乏線上即時分流環境與 A/B testing 數據，這兩項指標在本次專案交付時如何被客觀驗收？
-    **門檻量化缺漏**：Failure Criteria 提到「爭議案件錯派延誤處理超過 SLA」，但並未在文件中定義何謂「爭議案件」（指金額超過多少，或含特定法務關鍵字？）以及其「SLA」具體是幾分鐘或幾小時？
-  **追問**：如果離線評測中 Accuracy 達標，你打算用何種模擬數據或測試流程來驗收「轉單率降低 40%」這個商業指標？

## ④ Baseline 是否合理？

- **樣本基數與顯著性疑慮**：以 Week 1 的 src/rule_baseline.py 為比較基準在概念上合理（提供透明可解釋的非 AI 對照組）。但在 100 筆資料中，Baseline Accuracy 已達 0.950（僅錯 5 筆）；若 Success Criteria 要求 Accuracy ≥ 0.970，代表模型最多只能錯 3 筆。
- **追問**：在僅 100 筆的小樣本測試集下，錯 5 筆（Baseline）與錯 3 筆（複雜 AI）在統計上極可能是抽樣隨機誤差，如何證明複雜模型帶來的「增量價值」是真實的而非過擬合？
 
## ⑤ 是否有未定義的 failure case？
- **領域外與無意義輸入（OOD / Garbage In）**：目前 4 個標籤未涵蓋「非客服問題」（如「哈哈笑死」、「隨便貼的亂碼網址」或空白訊息）。現行設計會強行將其歸類至 4 類之一，導致錯誤分流。   
- **極短文本與問候語**：當顧客僅輸入「請問有人在嗎？」或「客服」時，模型若給出高信心度分類，會直接造成分流失敗。   
- **追問**：若使用者輸入完全不在 4 個類別範圍內的訊息，系統的分類邊界為何？是否需要定義「無效輸入／其他（out_of_scope）」作為 Failure 條件或獨立處理機制？ 

# AI Review Record

## Finding 1 (Target 可驗證性與複合意圖邊界)
- **AI Reviewer**: Target 目前為互斥 4 選 1，但真實對話常出現跨領域複合語句（如同時提到退貨與帳號密碼），缺乏客觀的標註準則與多數決仲裁機制。
- **Decision**: Accept
- **Reason**: 驗證集必須具備客觀唯一真值（Ground Truth），否則離線評估指標（Accuracy / Recall）將失去驗證效力。
- **Change**: 增訂標註優先級原則：若單句同時包含多種訴求，以金流風險最高之 `refund_return` 為主意圖；標註人員意見分歧時由資深客服組長最終裁定。

## Finding 2 (Input 欄位冗餘與文字切分邊界)
- **AI Reviewer**: Input 列出「時間戳記」但文字模型未作特徵規劃；且未定義輸入是指「單一傳送訊息」還是「多輪合併」，遇無意義問候語易出錯。
- **Decision**: Modify
- **Reason**: 接受精簡無用特徵與明確輸入格式，但暫不擴大至多輪對話整合，以維持本週任務在單句分類的純粹性。
- **Change**: 移除 Input 中的「時間戳記」，純化為「使用者進線單則原始文字」；並增設前置過濾：若字數 ≤ 2 字（如「你好」）直接提示引導，不送入模型推論。

## Finding 3 (Success / Failure 之落地性與門檻量化)
- **AI Reviewer**: 「跨組轉單率降低 40%」在離線 100 筆展示資料中無法客觀驗收；且 Failure 提到的「爭議案件」與「SLA」缺乏具體數據定義。
- **Decision**: Accept
- **Reason**: 驗收指標必須能在目前的離線實驗環境下被評估，且失敗準則必須明確可量化。
- **Change**: 將 Decision/Value 成功條件補強為「離線混淆測試集之錯誤路由率降低 40%」；Failure 明確定義「涉及金額退款且處理時限要求 ≤ 15 分鐘之工單發生分流錯誤」。

## Finding 4 (Baseline 統計顯著性與小樣本疑慮)
- **AI Reviewer**: 100 筆資料中 Baseline 準確率已達 0.950（僅錯 5 筆），目標要求 0.970（最多錯 3 筆），在統計上極易受抽樣隨機性影響，難以證明 AI 增量價值。
- **Decision**: Modify
- **Reason**: 專案受限於課程提供的展示資料集規模，現階段無法任意擴增樣本；但評估確實不能僅看微幅的總分提升。
- **Change**: 不單以 Accuracy 差異作為唯一依據，改將「Week 1 Baseline 判定失敗的複合關鍵字混淆句（如退貨與物流衝突）」是否能被 100% 正確分類，作為衡量 AI 實質增量價值的核心驗證項目。

## Finding 5 (未定義的 Failure Case / 領域外 OOD 與問候語)
- **AI Reviewer**: 系統缺少對領域外無效輸入（如亂碼、無意義問候「在嗎」）的邊界定義，會導致系統強行歸類為 4 類之一而造成誤分流。
- **Decision**: Accept
- **Reason**: 模型無法處理非預期文字是典型的系統層缺陷，必須在規格中定義防護機制。
- **Change**: 在 Failure Criteria 加入「輸入非客服問題卻給出高信心度分類」；並在 HITL/Fallback 機制中明訂：最高機率低於 0.70 時判定為 `out_of_scope`，直接轉入常規人工接待。

# Mini Defense 準備紀錄

- **Q1: 你真正要預測/檢索的是什麼？**
  -  在單則客服進線訊息（Unit）上，以原始文字為 Input，預測出對應的 4 種意圖之一（Target），並輸出帶有信心分數的 JSON 格式（Output）。
- **Q2: 不用你的 AI，Baseline 是什麼？**
  -  採用 Week 1 的 `src/rule_baseline.py` 關鍵字規則程式，因其無需訓練、規則透明且已有 0.950 的 Accuracy，是驗證複雜模型是否具備實質增量價值的標準基準。
- **Q3: 哪種情況下即使模型分數很高，你仍判定系統失敗？**
  - 若整體 Accuracy 達標，但退款退貨（`refund_return`）等高風險意圖頻繁被誤判為普通物流；或是推論延遲過長導致介面卡頓、迫使客服改回手動分流，在系統實務上即判定為失敗。
